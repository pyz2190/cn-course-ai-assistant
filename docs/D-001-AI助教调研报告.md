## 三、学校平台调研结论（对应 D-002）

### 3.1 结论

以课程成员身份查看同济 Canvas，得到的是权限范围内的观察结果：

- 未发现 AI、智能助教、课程问答或学习分析入口
- 因未发现可用 AI 组件，无法验证其能否接入课程文件、题库或字幕
- 未获得 API、外部工具、LTI 或课程导出配置入口与凭据

详见 [D-002 第三节](D-002-Canvas平台AI能力调研.md#三逐项调研结果)。

### 3.2 这个结论的边界

**这不是对 Canvas 产品能力的判断，是对本校当前部署、在课程成员权限下
观察到的结果。** 团队没有管理员权限，无法排除这些能力在管理员层面
已经启用、只是不对课程成员可见。这一区分写在
[D-002 第 2.2 节](D-002-Canvas平台AI能力调研.md#22-这份结论覆盖什么不覆盖什么)，
总报告予以强调，因为它直接决定了对外汇报时能不能把"未开放"说成"不具备"。

### 3.3 这个结论如何决定了项目的形态

因为团队当前没有获批的平台资料通道，本项目现阶段采用
"独立系统 + 人工上传"路线，同时保留以后接入 Canvas 的适配器边界：

- D-003 的知识库入库流程第一步（S1 采集）明确写"全部为人工操作"
- D-003 第 7.1 节记录了真实课程资料尚未进入主分支的现状
- D-007 的部署方案默认离线，不依赖任何校方接口
- D-009 第三节列出的 7 项待申请接口，全部是"如果将来打通了会怎样"

因此 D-002 不是一份孤立的调研，它是理解本项目为什么这样设计的前提。

## 四、知识库与问答库结论（对应 D-003）

### 4.1 知识来源与建设流程

八类知识来源、七阶段入库流程（采集→授权审查→解析→切块→审校→版本登记→更新维护）
的完整设计见 [D-003 第二、三节](D-003-知识库与问答库建设方案.md#二知识来源清单)。
总报告只强调一条贯穿全文的约束：**无法定位到章节或知识点的内容一律不入库**，
这是保证"回答可核对到课程资料"这一 RAG 价值主张（见第五节）不落空的硬性门槛。

### 4.2 问答库的规模与局限

30 题、六类各 5 题，数量与类别覆盖达标。但这些题目来自课程知识结构、
教材章节和任务场景，**不是由真实学生提问频次统计得到**。后者需要讨论区、
答疑记录或上线后的查询日志，而团队当前未取得这些数据。这个局限记在
[D-003 第 5.2 节](D-003-知识库与问答库建设方案.md#52-选题依据)，
意味着问答库目前是一份"预期会问什么"的初始基线，还没有被真实使用验证过。

### 4.3 当前可复核状态

主分支可用以下命令校验评测数据：

```bash
python scripts/run_evaluation_pipeline.py validate
```

2026-08-30 的校验结果为：问题 30 条、标注 30 条、正式评测集 0 条，数据结构校验通过。
30 条标注均处于 `pending_review`，因此当前没有正式评测基线，也不能据此给出检索
命中率或模型效果结论。语料为 22 个 mock Chunk（中文 11、英文 11），仅用于原型和
自动化测试，不代表真实课程资料覆盖率。完整边界见
[D-003 第七节](D-003-知识库与问答库建设方案.md#七当前状态与已知缺口)。

## 五、AI + 向量数据库 + RAG 技术结论（对应 D-004～D-007）

### 5.1 为什么是 RAG

课程问答的四个特征恰好对应 RAG 的四项能力，完整论证见
[D-004 第 1.5 节](d-rag/D-004-rag-technical-solution.md#15-rag-为什么适合课程问答)：

| 课程问答的要求 | RAG 的对应能力 |
|---|---|
| 答案要能核对到章节页码 | 检索片段携带完整元数据，引用不是事后装饰 |
| 宁可拒答也不能编造 | 无证据时返回安全拒答；实现与测试见 D-004 |
| 资料常年更新 | 知识在语料而非模型权重中，更新资料无需重新训练 |
| 课程语料规模小但要求精确 | 聚焦语料提高检索信噪比，天然适配小规模场景 |

### 5.2 技术选型结果

| 层 | 选型 | 依据 |
|---|---|---|
| 编排 | 原生轻量编排 `RagService` | [D-006](d-rag/D-006-rag-framework-comparison.md)：链路短、边界显式、不引入平台依赖 |
| 向量库 | Qdrant | [D-005](d-rag/D-005-vector-database-comparison.md)：内存/本地/远程三态统一、payload 过滤契合元数据模型 |
| Embedding | 默认离线哈希，正式模型 `BAAI/bge-m3` | [D-007 第 1.1 节](d-rag/D-007-finetuning-deployment-analysis.md#11-embedding) |
| Reranker | 默认离线词项重叠，正式模型 `BAAI/bge-reranker-v2-m3` | [D-007 第 1.2 节](d-rag/D-007-finetuning-deployment-analysis.md#12-reranker) |
| 生成 | 默认离线抽取式，可选 OpenAI-compatible | [D-004 第 7 节](d-rag/D-004-rag-technical-solution.md#7-两种运行模式) |

各项选型的对比依据记录如下：
D-005 对比了 Chroma、Qdrant、Milvus 三家共 9 个维度；
D-006 对比了 LangChain、LlamaIndex 两条开发框架路线与
Dify、FastGPT、RAGFlow、MaxKB 四个开箱平台。

### 5.3 引用安全

检索到证据不等于回答可信——模型仍可能在生成阶段编造资源名或页码。
本项目的对策是**服务端强制回填**：`Citation` 的资源名、章节、页码、
摘录全部由服务器从 `ChunkMetadata` 回填，模型输出只提供事实句和
证据 ID，不存在的 ID 会被直接丢弃。机制见
[D-004 第 6 节](d-rag/D-004-rag-technical-solution.md#6-生成与引用安全)，
相应行为由服务测试覆盖；正式评测结果需等人工审核后的评测集生成后再报告。

### 5.4 微调与部署结论

**是否微调：** 本轮不做。RAG 与 LoRA 的适用边界很清楚——
课程事实、协议细节、页码引用这类"会变、需要来源"的内容优先 RAG；
固定语气、固定格式这类"稳定行为风格"才考虑 LoRA。
课程问答的核心诉求恰好全部落在前者。完整边界表见
[D-007 第二节](d-rag/D-007-finetuning-deployment-analysis.md#2-rag-与-lora-的适用边界)。

**怎么部署：** 三种方式（本地 GPU / 云端 API / 校内平台）对比见
[D-007 第三节](d-rag/D-007-finetuning-deployment-analysis.md#3-三种部署方式对比)，
结论是分阶段推进——当前 Demo 全离线，有网络时可接 OpenAI-compatible 服务，
真正的正式试点要等 B/C 提供真实获批资料后再建评测基线，
校内平台是否可用仍是[待确认清单](d-rag/D-007-finetuning-deployment-analysis.md#5-校内平台待确认清单)。

默认全离线也适应当前未取得校方平台接口的条件；如果 D-009 第三节的
接口申请有进展，D-007 的部署方案可以随之推进到"有网络的演示增强"档位。

## 六、任务引擎结论（对应 D-008）

### 6.1 设计概览

六类任务类型全部落地：基础学习、协议分析与仿真、案例分析、创新挑战、
项目实践、排错。每类都有一个可运行的 Demo 任务实例。完整设计见
[D-008 第四节](D-008-任务引擎设计方案.md#四六类教学任务详细设计)。

### 6.2 任务如何关联知识点、资料、试题和 AI 反馈

任务模型 `TaskTemplate` 当前强制携带以下四类字段：

| 关联对象 | 回答的问题 | 约束 |
|---|---|---|
| 知识点 | 这个任务在教什么 | 至少一个 |
| 课程资料 | 学生去哪里学 | 至少一个 |
| 完成判据 | 怎么判断任务可以结束 | 至少一条 |
| AI 反馈 | 学生卡住时何时介入 | 至少一条 |

当前主分支的 `TaskTemplate` 和 `TaskPublishRequest` 没有 `exercise_ids`，也没有
`/api/v1/exercises` 路由。因此“任务关联独立试题”只能作为后续接口需求，不能写成
已实现功能。现有模型与扩展清单见 [D-008 第三、八节](D-008-任务引擎设计方案.md)。

### 6.3 与 Demo 的关系

六类任务在 D-010 的 Demo 中全部可交互：任务列表、详情切换、
关联知识点解析为可读名称、AI 反馈介入点展示，均在浏览器中可验证。

## 七、接口需求结论（对应 D-009）

### 7.1 接口状态分类

D-009 区分三种状态：

- **第三节：Canvas / 学习平台 API 需求，全部待申请**，
  由 D-002 的调研结论推导而来（P1 课程文件 API、P2 课程导出、
  P3 LTI 1.3、P4 字幕通道、P5 题库、P6 讨论区、P7 数据合规口径）。
- **第四至六节、八至九节：当前主分支已实现的接口**，以
 `contracts/openapi.json` 为准，共 24 个操作。
- **第七节：试题接口需求**，当前尚未进入主分支实现。

### 7.2 一条关键设计原则

**Canvas 专有字段不得进入领域模型和前端。** 一旦第三节的接口获批，
主要改动应限制在 `apps/api/app/adapters/` 的 Canvas 适配器，
把 Canvas 字段转换为现有领域模型。认证入口、权限提示和同步状态界面仍可能需要调整，
因此不能承诺前端和其他层“完全不改动”。
这也是本项目端口化架构（见
[D-002 第 4.3 节](D-002-Canvas平台AI能力调研.md#43-两条落地路径)）
真正要解决的问题：让"平台侧没有开放"这一现状可以随时逆转，
而不需要推倒重来。

## 九、现状与验证边界

调研任务要求"如果时间允许可搭建可运行原型"——本项目做到了原型，
但原型不等于完整系统。以下按"已验证 / 未验证 / 待补"三档分类。

### 9.1 已验证（有实测数据或自动化测试支撑）

- 评测数据结构校验通过：问题 30 条、标注 30 条、正式评测集 0 条
- 系统的离线模式、契约检查、API/前端测试和生产构建纳入 CI
- 任务模型在代码层强制要求知识点、资料、完成判据和 AI 反馈字段

### 9.2 未验证（方案已定，缺真实数据或人工环节）

- **问答库质量**：30 条标注全部 `pending_review`，正式评测基线尚未产生，
  阻塞项是人工交叉评审，这一步不能自动化
- **检索与生成效果**：没有已审核的正式评测集，不能给出可发布的命中率、
 正确率或幻觉率
- **正式模型效果**：`BAAI/bge-m3`、`BAAI/bge-reranker-v2-m3` 只是选型结论，
  尚未用真实课程语料和 C 的评测集实测召回率、延迟与成本

### 9.3 待补事项

- **Canvas 接入**：完全未开始，取决于 D-009 第三节接口能否获批
- **真实课程资料**：知识库当前 100% 为 mock 样例，S1–S3、S6 的真实内容
  需课程组提供
- **字幕、论文、技术博客三类语料**：当前 mock 语料未覆盖，获取方式与授权仍需确认
- **试题接口与任务关联**：当前主分支未实现 `/api/v1/exercises` 与 `exercise_ids`
- **周报与实习报告**：任务要求的过程性交付物，本报告不涉及，需单独跟进

## 十、下一步执行顺序

汇总各分册的"下一步"，按依赖关系给出建议顺序：

```text
1. 向学校提出 D-009 第三节的接口申请（P1/P2 优先）
2. 课程组提供真实课程资料（S1-S3、S6），启动 D-003 第三节入库流程
3. 补齐语料缺口：任务类指导资料、实验交付物规范（对应 D-003 §7.4 的分析）
4. 交叉评审把 ≥15 条标注推到 approved（人工环节，不可自动化）
5. 同步正式评测集并执行首次正式基线，产出 baseline.md
6. 用真实语料和评测集实测 D-007 选定的正式 Embedding/Reranker 模型
7. 根据实测结果决定是否推进"有网络的演示增强"或"正式试点"部署档位
```

第 1、2 步可以并行推进；第 4 步要求真实审稿人和时间戳，不能用自动化结果替代。
